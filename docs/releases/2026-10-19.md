# October 19–25, 2026 release — PR #289

This is the deployment checklist for the combined weekly release, including
PR #290's Sunday School design and the follow-up UI/calendar work. Do not deploy
individual features with only part of the required schema.

## Required schema bundle

One committed migration is new relative to this release's `main` baseline:

| Order | Migration | Included schema changes |
| --- | --- | --- |
| 1 | `20261023020000_family_matching_history` | `SundaySchoolFamily.matchingHistory` (nullable JSONB); `SundaySchoolFamily.matchingPhones` (non-null text array, empty default); `SundaySchoolChild.familyDetailsOverrides` (nullable JSONB) |

The three additions are already bundled in that migration. Do not create a
second migration for the same columns or rewrite migrations already applied.
The migration does not consolidate families or backfill contact records.

The read-only production audit on October 23 found this as the **only pending
migration**. Earlier migrations in this checkout were applied, with matching
checksums. The audit found the three missing columns above and no missing enum
values or unfinished migrations. Re-run the preflight before release because
production and this branch can change.

Class lesson subscriptions, the class-context labels, persistent class box,
attendance-chart cleanup, and What’s new require **no additional schema or
environment changes**. Calendar links use the existing `NEXTAUTH_SECRET` and
app origin. Phone subscriptions require the new code on a public HTTPS origin;
localhost links are for development inspection only.

## Validate and deploy in order

1. Freeze/review the release head and confirm its user-facing notes and actual
   deployment date in `lib/release-notes.ts`.
2. Run the read-only preflight with the target environment's configured URLs:
   `bun scripts/check-release-schema.ts`. It lists pending migrations, missing
   Prisma columns/enum values, checksum mismatches, and unfinished migrations.
   It exits 1 while anything is pending; it never changes the database. It is a
   migration/column/enum preflight, not a complete index/constraint drift diff.
3. Create an isolated Neon branch from production. Point only the local/preview
   environment at it and apply committed migrations with `bun db:deploy` using
   its **direct/unpooled** URL for schema operations. Run the preflight again;
   require empty findings. Never use production for fixture-based tests.
4. Validate the roster, families, child create/edit/import, and family matching
   on that isolated branch. Run `bunx tsc --noEmit`, `bun lint`, `bun test:run`,
   and `bun run build`. Check Apple/Google calendar link creation and the ICS
   response; subscription refresh happens on the calendar provider's schedule.
5. Before the separately authorized production schema step, record a recoverable
   production snapshot/backup and the previous working deployment. Apply all
   committed pending migrations explicitly with `bun db:deploy` and production's
   direct/unpooled connection. Builds never apply migrations. Do not use
   `db:push` or mark migrations resolved to conceal checksum/schema mismatches.
6. Require empty preflight findings, verify `/api/health`, then deploy this
   release's code and smoke-test roster loading, class switching, Daily readings,
   lessons, calendar subscriptions, and What’s new. The app uses the pooled URL.
7. Family consolidation is a separate deliberate admin action after deployment:
   **Match existing families** on Children. It is not part of the migration or
   an automatic release script.

## Rollback

Return to the previous application deployment and leave these additive columns
in place. Do not drop columns or undo family links as part of a code rollback.
If family matching has already been run, use its retained history and the
pre-release snapshot to plan a separate data recovery.

[class calendars](../sunday-school-mode.md#class-lesson-calendar-subscriptions),
